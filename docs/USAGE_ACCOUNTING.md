## 2026-11-23 每日总数与明细不一致

只读访问线上管理 API，确认 `tcl_m7642` 在 `2026-11-22` 的累计常规用时为 `3600000` 毫秒，而三个时段合计为 `1628588` 毫秒（约 27 分 9 秒），缺少 `1971412` 毫秒（约 32 分 51 秒）的时间定位。快照保存在本机忽略目录 `.tools/validation/usage-records/`。

旧后台根据两次累计上报的差值和接收时间推算时段：首条上报不产生明细，后续每条最多产生两分钟区间。首次携带的累计数、长时间离线后的增量因此不能完整进入明细。合并相隔不超过两分钟的区间后再用结束减开始，也会把中间未观看的空隙算成用时。

进一步只读检查 ECS journal：当天用时接口在 11:10:54–13:36:11 出现 410 次 HTTP 401；13:37:14 有绑定成功记录，13:37:28 开始出现成功用时上报。这支持认证失败后首次成功补报触发明细遗漏的路径，不能简单归因为断网。原日志没有请求体，不能断言全部差额在某一次请求中丢失。使用线上原版 handler 和构造的初始累计数，通过本地 HTTP 请求可复现完全相同的总数和三个时段。

修复后，电视把实际区间及累计毫秒数与每日用时一起同步保存，使用同一个 32 日期历史账本。区间区分计入限额、奖励观看、家长放行和答题；后两种不增加每日额度已用数、不扣奖励。答题按实际题目/反馈显示且亮屏的时间采样，排除待机、PIN 输入和锁定页。首页 PIN 暂停计时的观看也归为家长放行。清零今日用时时只清除计入限额区间，保留其余类型。当前日期的每次上报发送完整 `usageIntervals` 快照，后台按各类型分别检查累计量不回退，避免普通额度固定时旧快照抹掉新增放行或答题用时。允许时段裁剪及额度裁剪使用同一份采样区间。

后台仍可合并相隔不超过两分钟的连续时段，但独立累计实际用时，不把间隙计入。旧数据无法定位的差额单列为未定位时长，不伪造起止时间、不削减累计数。新增 `UsageIntervalTest` 和 API 回归测试覆盖首条离线上报、重复及过期快照、短暂停顿、升级前记录保留、日期恢复、奖励分流及用时重置。

修复需要同时更新后台与电视应用。已有历史差额无法仅凭累计数还原到某个具体时段；跨日离线期间尚未发送的历史日期也不会由当前日期上报自动补传。本次排查没有修改线上记录或规则。

## 2026-11-12 排查

用户反馈：待机唤醒或完整重启多次后统计不准确，偶尔剩余额度重新变成 60 分钟。

检查电视 `10.0.0.8` 时，系统日期为 `2026-11-12`、时区 `Asia/Shanghai`、自动校时开启；本地仍保存 `used_millis=1362405`，约 22 分 42 秒。该次读取没有看到清零，已有日志也不足以证明此前发生过日期跳变。因此，以下是代码确认存在的问题与对应修复，不能等同于已在真机重现用户遇到的整次复位。

## 确认的代码问题

1. 原 `resetForNewDay` 只检查当前日期与保存日期是否不同，任何日期变化都会清零，并删除已执行的远程重置命令 ID。若开机时日期回退、随后联网校正，同一天会被当作两个新日期，原本的已用时间无法恢复；旧重置命令还可能再次执行。
2. 原用时采样间隔为 30 秒，使用异步 `apply()` 保存，未监听关机，也未在服务销毁前补结算。直接重启、断电或进程被杀可能丢失末尾未结算的用时；多次操作会累积误差。异步保存本身不能解释整天用时一定丢失。
3. 同步完成和重复启动服务时，有些分支直接改写屏幕状态，没有先结算旧状态。状态变化与采样交错时，整个尚未结算的区间可能被归入错误状态。原采样还用区间结束时的允许时段判断，可能丢掉时段边界前的合法用时。
4. 原累计使用 `min(已用 + 本次, 额度)`，如果规则额度降低与采样发生交错，可能把已经记录的已用时间向下覆盖。
5. 原服务重建时直接相信磁盘上的“悬浮窗正在显示”标记。进程异常退出后，这个标记可能残留，导致实际没有弹窗时仍暂停计时；现在同时核对悬浮窗服务是否在当前进程运行。

## 修复行为

- `DailyUsageLedger` 持久保存当前日期与最近 32 个历史日期的用时、临时延时、远程重置 ID 和重置时间。遇到未见过的旧日期时保留当前日期；未来日期跳变后校正，恢复该日期的记录。正常跨本地午夜仍开始新的一天。
- 计时累计和日期切换使用同步 `commit()`。普通采样间隔缩短为 10 秒，屏幕关闭、正常关机、服务销毁时立即补采样。临时延时也同步保存。
- `UsageSampleTracker` 用单调递增的 `elapsedRealtime` 计算区间长度，先结算旧状态，再应用新的屏幕或悬浮窗状态。待机和答题/锁定弹窗期间不累计；重建服务以本次启动时间为基准，不把关机时间算成观看时间。
- 允许与禁用时段按区间逐段计算；远程重置时间和答错锁定截止时间会裁剪可累计区间。额度减少只影响剩余额度，不减少已用总数。
- 日期切换、保留旧日期的决定写入 `TvParentalUsage` 日志；服务 dump 同时显示统计日期、系统日期和已用毫秒，便于下次定位。
- 每次开机启动计时服务、待机唤醒时立即向后台上报当天累计用时，成功后继续每分钟上报。发送失败每 5 秒重试，网络恢复时立即重试；同一时间只发一个请求，上报中收到新的立即上报请求时补发一次。上报通过原 `/api/v1/device/usage` 接口完成。

## 验证与边界

`UsageAccountingTest` 覆盖反复进程重建、日期回退、未来日期跳变后校正、跨本地午夜、降低额度、历史记录保留上限、反复待机、悬浮窗暂停、关机末尾结算和状态刷新交错。

```powershell
# 先按 docs/README_BUILD.md 设置当前机器的 JDK，再运行：
.\gradlew.bat testDebugUnitTest
```

突然断电或无法执行回调的进程强杀，仍可能丢失最后一次持久化之后的少量用时；服务正常调度时通常是最近 10 秒内的区间。Android 长时间挂起或杀掉服务时，不能承诺固定误差上限。离线状态无法可靠判定任意系统时间是否正确，本修复防止日期切换永久抹掉已有记录，并非独立的可信授时服务。

本轮只读取真机状态，未主动关机、重启或更改电视系统时钟。升级前已经丢失、且没有保留副本的用时不会自动重建。
